# Global token index: schema and rationale

Implemented 2026-10-15 in the supplied checkout (`feat/improve`; the requested `poc/token-discovery` branch was absent). The old design had 130 passing tests. The replacement had 93 passing tests, with the obsolete backfill/refold/tail/worker tests replaced by global-index, repair and readiness coverage; the on-demand balance work brings it to 105, and restoring the near-realtime tail on the global index brings it to 131. `npx tsc --noEmit -p .`, `npm test`, `npm run lint` and `git diff --check` all pass. No network measurements were made during this redesign.

**Serving modes update (2026-10-19).** Account reads now serve stale published snapshots and partial bootstrap coverage. The offline Vitest/PGlite suite grew from 168 to 177 passing tests; TypeScript, lint and diff checks pass. No schema change or live load benchmark was needed for this change.

**Status: near-realtime with finalized durability.** The assignment asks for data up to the current block. The durable global index is finalized-only (~13 min behind the tip); the restored tail journal serves the tip (~12 s slots) by default (`finality=latest`) and degrades to the finalized view with `tailError`, never to an error, when it is unhealthy or stale.

## Architecture

The target is approximately **1M accounts, 180M Transfers in the current ~265k-block window, ~5M additional Transfers/day, and 15–40M holder/token pairs** (planning estimates). Each finalized Transfer is stored once, independently of account requests. Raw history is the durable source for summaries and NFT ownership. Storage grows with chain activity; ingestion RPC cost is O(blocks), not O(accounts × blocks).

The resumable bootstrap (`src/bootstrap/`) pins [S, B], verifies the staged header chain and applies segments in any order. Every segment commits raw transfers, holdings, NFT winners and its applied marker together; publication creates the contiguous cursor at B after all segments and headers validate. Before publication, account reads serve applied data with explicit partial coverage; no run means unavailable. The follower then bulk-appends contiguous ranges for every account, including bounded catch-up after an outage. No account request schedules ingestion.

## Schema

Every table includes a stable registry **smallint network ID**, independent of the EVM chain ID. Addresses use **bytea with a 20-byte CHECK**; block/transaction hashes use **bytea with a 32-byte CHECK**. PostgreSQL has no `bytea(20)` type. Blocks, block timestamps, counters and revisions are bigint. Application times are bigint epoch milliseconds. ERC standards are smallint 20/721; TypeScript still exposes `erc20 | erc721`. Uint256 amounts/IDs use **numeric(78,0)** with 0…2²⁵⁶−1 checks, never floating point or lexical decimal ordering.

| Table | Key and indexes | Purpose |
|---|---|---|
| `ingestion_state` | PK network | Start block, contiguous cursor/hash/time, observed finalized head/hash/time and check time, repair revision. The cursor row serializes append/repair; progress is never committed separately |
| `block_headers` | PK (network, number) | Complete number/hash/parent-hash/timestamp chain, including empty blocks and anchor. ~265k rows are small next to 180M events |
| `transfers` | PK (network, block_number, log_index); B-trees (network, from, block DESC, log_index DESC) and the equivalent to-index; partial ERC-721 index (network, token, value, block DESC, log_index DESC) | Idempotent raw event identity, range delete/read, newest-first account history, and latest surviving NFT event during repair. One `value` stores amount or token ID, without a duplicated NFT ID column |
| `holdings` | PK (network, holder, token); index (network, token, holder) | First/last block, standard and bigint sent/received counts. Account tokens use the PK; interacted holders use the reverse index. A summary is not evidence of a positive balance |
| `nft_ownership` | PK (network, token, token_id); index (network, owner, token, token_id) | One current owner per NFT. Latest (block, logIndex) wins. Zero owner represents a burn and is excluded from held-item reads |
| `balance_snapshots` | PK (network, account, token); index (network, block_number) | Exactly one value or error, read block/hash/time and repair revision. Account lookup uses PK; block index invalidates snapshots in repaired ranges, including accounts absent from changed logs |
| `tail_blocks` | PK (network, number) | Unfinalized parent-hash chain above the cursor; replaced on reorg, pruned in the cursor transaction. Bounded by `TAIL_MAX_AHEAD_BLOCKS` |
| `tail_transfers` | PK (network, block_number, log_index); (network, from, block DESC, log_index DESC) and the `to` equivalent | Every Transfer of the tail blocks with the same column types as `transfers` (smallint network, bytea, numeric(78,0)); overlay and latest history read the account indexes |
| `repair_queue` | PK (network, from_block, to_block) | Pending suspect ranges, reason and creation time; identical requests deduplicate. Per-network ordered work uses the PK; no unused status index |

There are no surrogate transfer IDs, transaction-hash lookup indexes, redundant token metadata tables or global address registry. All writes enter through the store; it validates header/log membership once per batch rather than adding a foreign-key lookup per event. Binary and numeric codecs are centralized in `src/store/columns.ts`; registry name conversion is centralized in `createStore`.

### Partitioning decision

This baseline deliberately uses **one transfer table**, after considering declarative block-range partitioning. The critical arbitrary-account history request has no narrow block window. Two global ordered indexes can return bounded pages directly; block partitions would require multiple local-index probes/merge planning, especially for quiet accounts. The primary key already constrains range deletion and append derivation. Only the partial NFT index adds write cost beyond identity and the two history indexes, and repair actually queries it.

The tradeoff is larger indexes and table-wide vacuum/reindex maintenance as ~5M rows/day accumulate. Partitioning could localize that maintenance and large replacements. This is a PoC choice, **not a measured claim that an unpartitioned table meets the final latency target**. Before the 180M-row bootstrap, benchmark history plans, ingestion, repair, WAL and vacuum against a block-partitioned variant. If selected, use a drizzle-kit `generate --custom` migration plus partition provisioning; drizzle-kit cannot declare a partitioned parent. No partitioning or custom migration is currently installed. The fresh baseline was produced by `npm run db:generate`, without editing generated SQL.

## Store invariants and read behavior

`initialize`, `observeHead`, `appendRange`, `replaceRange`, `rebuildRange`, `indexState`, `enqueueRepair`/`repairs`, `readAccount`, `transferHistory`, `tokenHolders`, `balances`, `saveBalances` and the tail journal (`tailTip`, `tailBlocks`, `appendTailBlocks`, `rewindTail`, `wipeTail`) form the store API.

Append requires complete ordered headers, a matching predecessor, matching event hashes and an end no later than the observed finalized head. Raw inserts use 1,000-row batches. SQL groups the committed raw range into summaries and chooses NFT winners; both self-transfer directions count once while the raw identity exists once. A fully committed replay is a no-op; partial overlap is rejected and changed historical data must use replacement. Mixed observed standards for a contract resolve deterministically to ERC-721 in the summary (721 > 20); raw rows retain their individual classification.

Replacement captures old and new participants before rebuilding. It deletes/inserts the range in one transaction, verifies both neighboring headers and rebuilds **all retained history of each touched account once per direction**, avoiding a separate account-history scan per token. Touched NFT IDs use the partial latest-event index, so an earlier or later event outside the repaired range restores the correct owner. Vanished pairs/items disappear. Rebuild-only operations use existing raw rows and do not certify suspect source data or clear its repair queue.

Replacement/rebuild invalidates affected caches and increments a network revision. `saveBalances` checks that revision and the canonical block hash under a shared cursor lock, preventing a delayed pre-repair read from resurrecting invalid cache data. Normal cache writes preserve newer snapshots and read times. RPC errors marked transient are returned but never stored.

Account snapshots and history pages use repeatable-read transactions. History runs two limit-bounded ordered index scans, excludes self-transfers from the received branch and merges at most 2 × (limit + 1) rows. Pagination retains its original upper block bound and revision; repair requires a 409 restart. Account-token results sort only the matching summary rows, so another last-block index was not added.

Readiness and availability are separate, both derived from shared database state. `status()` and `/health` expose `serving: full | stale | partial | unavailable`. Readiness remains false during bootstrap and follower catch-up, but account endpoints and health return 200 for stale/partial modes. Published indexes behind the finalized head, with an expired observation, or without recent cursor progress serve the exact finalized cursor snapshot with `stale: true`, the existing reason string in `staleReason`, and lag fields. Latest requests omit the tail and report the reason in `tailError`. `MAX_SERVE_LAG_BLOCKS` defaults to 7200 (~1 day at 12 s/block), inclusive; greater observed finalized lag returns 503. An old observation alone continues serving stale indefinitely: head/source failures do not renew its timestamp and do not establish a known current block distance. Pending repair and same-height cursor/head hash mismatch always return 503 `not_ready` with `Retry-After: 5`, as do missing run/index or initial head observation.

Bootstrap reads select the run, applied segments and account rows in one repeatable-read snapshot. Coverage uses sorted merged inclusive intervals, `coveredBlocks`/`totalBlocks`, S and pinned B/hash. Only applied segments contribute; legacy UNLOGGED staging is excluded until per-segment replay commits. Holdings and NFT ownership are already queryable before publish. Responses use `status: partial`, `complete: false`, a note explaining lower-bound counts/last-seen blocks, potentially earlier first-seen blocks and outdated NFT owners across missing later ranges. They omit single-block snapshot fields because B is a bound, not a complete snapshot. Even all-applied coverage remains partial until publish validates headers. Partial balance reads return an explicit omission reason and ownership verification is skipped, with no RPC. Partial history cursors are fenced by covered block count and a partial marker; any apply/publication requires a 409 restart. Published history cursor encoding is unchanged. No schema migration is needed.

## Removed behavior and the restored tail

Removed: tracked accounts/backfill targets, scan progress/range tables, per-account backfill scheduling and adaptive persistence, handoff/refold logic, per-account 202, active-account sets and background balance refresh. Standalone RPC/HyperSync comparison diagnostics remain outside runtime wiring.

The first global-index revision also removed the unfinalized tail, which left the service ~13 minutes behind the tip and so short of the assignment's "to the current block, near-realtime" requirement. It is **restored** (`src/tail/tail.ts`, migration `0002_tail_journal`) as a separate bounded journal that never advances or rewrites the finalized cursor. The leader-only, slot-aligned polling, parent-hash reorg rewind, depth/cursor wipe, fenced rewind/wipe on the observed tip hash, lagging-node handling, logs-match-header catch-up check, finality-stall bound and shared tip-time freshness are ported from the previous implementation with their tests. Differences on the new architecture: the tail stores every Transfer (no tracked accounts); it runs only once the global index is within an epoch of finalized; `appendRange` prunes it in the cursor transaction (wipe on hash mismatch) and a cursor-block repair wipes it.

Reads: `readAccount`/`transferHistory` read the tail tip and the account's tail rows in the same repeatable-read snapshot as the finalized state; discovery overlays them (counts, `lastBlock`, NFT holder) and history merges them flagged `unfinalized`. Balance snapshots carry a `canonical` flag computed against `block_headers`/`tail_blocks` in that snapshot; reuse at served block S of a read at R requires R canonical and no finalized or tail Transfer of the pair in (R, S], so a tail reorg of R or a tail Transfer invalidates it. `saveBalances` accepts a tail block only while it is the stored tail block at that height, and a newer snapshot on an orphaned block may be overwritten by an older canonical read.

## Alternative implementation: Subsquid, measured live

The same assignment was re-implemented on the latest Subsquid SDK in `../disquid` (squid-sdk 0.6.2, RPC only through `EvmRpcDataSourceBuilder`, Postgres with hot blocks, GraphQL). It ran live from block 26,104,555 to the head and then followed the head for 34.6 h. Full numbers, method and caveats are in [BENCHMARK.md](BENCHMARK.md), and the history is in PROGRESS §18.

| | Subsquid (`../disquid`), measured | i-see-u |
|---|---|---|
| Catch-up RPC | 1.02 calls/block: 106,084 calls for 103,617 blocks in 2 h 59 min | Bootstrap: about 1.01 calls/block RPC-only (derived). With HyperSync, 15 Quicknode calls for 2,001 blocks in 33 s (measured smoke run); full window not yet benchmarked end to end |
| Head RPC | 18.2k calls/day, about 11M credits/month | Tail: 1.26–1.5 header calls plus 1 `eth_getLogs` per block (measured, short samples), about 16–18k calls/day, about 9.5–11M credits/month |
| Reorgs | 8 live, all 1 block deep, rolled back by the hot-block change log | Tail journal rewind (tested, see §13) |
| Correctness | 0 mismatches against i-see-u's raw transfers: 386,213 ERC-20 pairs, 5,627 ERC-721 pairs, 12,381 NFT owners | Reference |
| API | One GraphQL process: about 3,000 req/s, p50 3.2 ms without balances | No live HTTP load test |
| Storage | 15 GB at 114.6k blocks, aggregates only, about 550 B/row | 60 GB at 272k blocks, raw transfers 46 GB plus holdings at about 240 B/row |

**What the framework gives:**
- reorg rollback through the hot-block change log;
- GraphQL CRUD generated from the schema;
- typed decoding;
- a path to Portal or multi-RPC failover through `EvmFallbackDataSourceBuilder`.

**What it costs:**
- **A custom RPC layer.** Without it the stock 0.6.2 RPC source fetches full blocks and unfiltered logs, polls `latest` every 100 ms (about 1M calls/day), exits on the first 429, and crashes on the first head reorg. The layer depends on two private SDK fields and should go upstream.
- **Bigger rows.** String entity ids make each row about 2.3× larger.
- **No raw history.** None is kept, so new derived data needs a re-index.

## Handoffs and limits

- **Bootstrap (done):** streaming sources, header verification, atomic out-of-order segment application, legacy replay and publication are implemented. Partial reads expose applied intervals before publication. Full-window throughput and concurrent PostgreSQL read/write load still need a live benchmark.
- **Repair runner:** select an alternate source, refetch suspect ranges, call replacement and monitor queue age. Header validation detects chain disagreement, not silent missing logs. Large repairs can scan heavy accounts (including mint/burn endpoints), hold the network writer lock and produce considerable WAL; read snapshots remain atomic.
- **Balances (done):** `src/balances/reader.ts` reads on request only, at the served block hash (tail tip by default, finalized cursor otherwise). It reuses a snapshot when the revision matches, its block is still canonical and the overlaid `lastBlock` ≤ read block (no finalized or tail Transfer since), except for always-refresh tokens, which with the tail are re-read at every new tip. It single-flights and window-batches pairs across accounts into shared Multicalls under the request limiter and deadline. A batch's RPC is aborted once every request waiting on it has given up (deadline or client disconnect); later requests then start a fresh read. Responses keep the read block and add `balanceValidAt`/`balanceCached`; see README for the rule and 1M-account cost math. Open: cross-replica coalescing/stampede control, the completeness of the always-refresh list, and errors are reused until a Transfer or repair.
- **Tail (done) open risks:** non-leader `/health` reports the tip loaded at startup (responses use the shared database tip); latest history pages are not reorg-stable; always-refresh tokens cost a read per poll at the tip; balances of a `finality=finalized` request are not cached while a newer latest snapshot exists; a stalled finality grows the tail to `TAIL_MAX_AHEAD_BLOCKS` × ~1k Transfers before it degrades.
- **SQD squid-sdk RPC source (evaluated 2026-10-15; built and measured 2026-10-16 to 18 in `../disquid`):** the stock 0.6.2 `EvmRpcDataSourceBuilder` forces full blocks (`transactions: true`), sends `eth_getLogs` with no topic filter and no range splitting, polls `latest` every 100 ms, sets `retryAttempts` to 0 (one 429 exits the processor), and crashes on any head reorg (`ForkException` carries a single ref, so `findRollbackIndex` returns -1). `../disquid/src/source` fixes all of these in a `DiscoveryRpcSourceBuilder` subclass with the same fluent API, without patching `node_modules`: header-only blocks, a topic0 pushdown with range splitting, a log/header block-hash check with refetch by hash, retries with timeouts, slot-aligned head polling, a cached finalized head, and fork ancestry rebuilt by parent hash. Measured: 1.02 calls/block during catch-up and about 18.2k calls/day at the head. Our RPC-only follower and tail cost about the same, while the HyperSync bootstrap is about 130× cheaper in Quicknode credits; 8 live reorgs handled; 0 parity mismatches against this repo's raw transfers ([BENCHMARK.md](BENCHMARK.md)). Risk: it relies on two private SDK fields (`EvmRpcStreamDataSource.inner`, `RpcClient.con`), guarded by asserts. The fixes should go upstream. Adopting it here would still mean rebuilding `appendRange`, repair and readiness on top of the hot-block store; it is a parallel implementation, not a drop-in.
- **Cancellation (2026-10-16):** request-path RPC work stops when its request gives up, through plain `AbortSignal` (Effect was evaluated and not adopted). `RpcRequestOptions.signal` aborts the in-flight fetch (viem's http transport takes a per-call signal), skips further attempts and cuts the token-bucket wait and backoff sleep; an abort is not an endpoint failure. `Limiter.run` passes the job a signal combining the caller's signal and `deadlineAt`, and an aborted queued waiter leaves the queue at once. `withDeadline` answers 503 at the deadline, then aborts the work; it also aborts the rest of the work when part of it fails (e.g. one of several balance batches). `scanAccountChunk` shares one controller, so the first failing direction aborts the other in flight. The ownership sweep is shared per block and bounded by its own deadline, not by one client's disconnect. Errors keep their mapping: a deadline is `unavailable(...)`, and a failed ownership sweep is now a 503 like a failed balance read (a sweep where only some chunks fail still returns per-item errors).
- **Runtime/scale:** full header verification costs one block-header RPC per ingested block, with bounded concurrency, plus unfiltered range log requests. It buys internal-chain and per-log fork validation; it is still independent of user count. No 1M-account load, 180M-row throughput or live PostgreSQL 18 multi-connection stress test was performed; tests use PGlite. The existing RPC retry/failover/rate-limit policy remains intact.
